# 知伴：答辩与演示指南

## 1. 答辩目标

答辩不应只展示"能聊天"，而应证明以下工程能力：

1. **记忆可控且会演化**：知道何时写、如何检索、冲突如何处理，也允许用户明确遗忘；更重要的是记忆会随用户变化而演化、随积累而自我去重——不是把每条信息静态存下来，而是一个会"自我更新"的记忆系统。
2. **工具可靠**：模型只提出意图，系统负责 schema 校验、权限、超时、重试、幂等和循环上限。
3. **上下文有预算**：不会无限拼接历史；通过筛选、摘要和压缩保留有效信息。
4. **不确定性可治理**：畸形 JSON、空答、429、5xx、超时和重复调用都有确定状态与降级。
5. **用户数据隔离**：认证上下文决定数据归属，记忆、会话、待办和工具执行均按用户过滤。
6. **产品可独立运行**：不依赖企业内部 DSL、仓库、账号和基础设施；离线 Mock 也能完成可重复演示。

推荐核心句：

> 知伴不是把大模型直接接到聊天框，而是用可测试的编排、记忆和工具边界，把不确定的模型能力约束成一个可用、可控、可恢复的个人助理。

## 2. 8～12 分钟故事线

建议将正式讲解控制在约 10 分钟，现场操作不超过 6 次，避免频繁切换窗口。

| 时间 | 内容 | 证明点 |
|---|---|---|
| 0:00～0:50 | 问题与目标 | 通用个人助理的价值不是一次回答，而是跨会话持续理解并完成行动。 |
| 0:50～1:40 | 产品边界 | 独立轻量、单 Agent、可控工具；首版不做企业 DSL、多 Agent、真实社交通讯。 |
| 1:40～2:40 | 架构图 | Next.js、FastAPI、PostgreSQL/pgvector、Redis、Worker 的职责与数据流。 |
| 2:40～4:20 | 演示一：偏好记忆 | 第一次明确告知偏好，新会话主动使用；展示来源与用户可控性。 |
| 4:20～5:10 | 演示二：明确遗忘 | 删除/tombstone、缓存/摘要失效，证明"记住"不是不可撤销。 |
| 5:10～6:30 | 演示三：创建并修改提醒 | Agent 选择工具、参数确认、UTC/时区、幂等和 Worker 投递。 |
| 6:30～7:30 | 演示四：搜索后总结 | Mock/真实搜索 adapter、来源保留、外部内容视为不可信数据。 |
| 7:30～8:35 | 演示五：故障降级 | 模型或搜索超时，展示超时预算、有限重试和可读回复。 |
| 8:35～9:30 | 上下文与安全 | Token 预算、compaction、跨用户过滤、SSRF/Prompt Injection 防护。 |
| 9:30～10:00 | 测试与结论 | 展示测试分类和实际报告；未实测数字只称"验收目标"。 |

若只有 8 分钟：压缩产品背景和架构到 1.5 分钟，搜索演示只展示结果，不现场输入；保留记忆、提醒、故障三条主线。

若有 12 分钟：增加跨用户隔离证据、SSE 断线恢复或 trace 讲解，但不要增加临时功能。

## 3. 主演示脚本

### 3.1 开场

建议表述：

> 普通聊天产品能回答当前问题，但个人助理还需要记住对用户长期有价值的信息、在合适时主动使用，并能安全地执行工具。知伴重点解决的不是 Prompt 本身，而是记忆、上下文、工具调用和异常处理的工程闭环。

屏幕准备：

- 左侧为产品界面，右侧不长期展示终端。
- 首页显示当前为 `Demo/Mock` 或 `Live` 模式，避免把 Mock 搜索说成真实联网结果。
- 架构图使用静态图片或文档，避免现场启动绘图工具。

### 3.2 演示一：第一次告知偏好，跨会话主动使用

**用户输入**

> 我喝咖啡不加糖，请记住。

**预期可见行为**

- 助理确认记录的是"咖啡甜度偏好：不加糖"，不扩写为未表达的健康结论。
- 记忆面板出现一条带类型、来源和状态的记忆。
- 新建会话后输入：

> 给我推荐一种下午喝的咖啡。

- 助理主动考虑"不加糖"偏好，并在 UI 允许的情况下标注"使用了已保存偏好"。

**讲解要点**

- 写入不是把每句话永久保存，而是"候选提取 → schema/类型校验 → 去重/冲突判断 → 持久化"。
- 检索先按当前用户过滤，再按相关性、类型、置信度和时效排序。
- 只把少量相关记忆注入上下文，受 Token 预算限制。

**记忆演化的深度（可选加分，体现三期演进）**

当用户改变一个既定偏好（"我不吃辣" → "现在能吃辣了"），系统不是机械地记两条，而是：

- **自然语言 fact 范式**：记忆以一句自然语句存储（如「用户不喜欢吃辣」），而非易出错的三元组（避免"用户 喜欢吃 用户 不喜欢吃辣"这类抽取畸形）。
- **语义去重**：主动/自动两条提取路径之间做词法相似度去重（含否定极性判断），已记过的信息不重复记。
- **语义调和（reconcile）**：用户明确说"记住 X"时，模型判断 `add/update/supersede/ignore` 四选一，工程层校验后执行——「喜欢辣」→「不喜欢辣」自动取代旧值，而非并存两条。
- **演化链**：记忆变化时保留历史（`superseded_by` 串联），支持"你之前……现在……"的时间追问。

核心原则贯穿始终：**LLM 只提议，确定性代码裁决**，杜绝幻觉误删。

### 3.3 演示二：明确忘记

**用户输入**

> 忘记我的咖啡偏好。

**预期可见行为**

- 助理确认遗忘范围。
- 记忆面板中该记忆被删除或标记为非活跃。
- 再开新会话询问咖啡推荐，助理不再使用"不加糖"。

**讲解要点**

- 遗忘会失效检索缓存和摘要引用。
- 使用 tombstone/版本信息，避免后台再次从旧消息静默提取同一事实。
- 旧消息是否保留与"活跃记忆是否可用"是两个不同的数据生命周期问题。

### 3.4 演示三：创建并修改提醒

为避免"明天"随答辩日期变化，演示数据应使用固定显示日期，或在重置时按当前日期动态生成。

**用户输入**

> 明天上午 9 点提醒我提交答辩材料。

**预期可见行为**

- 助理回显绝对日期、`Asia/Shanghai` 时区和事项。
- 若日期/时区有歧义，应先确认，不强行创建。

随后输入：

> 改到上午 10 点半。

**预期可见行为**

- 同一提醒更新，不新增一条重复提醒。
- 待办/提醒面板只显示最新时间。
- 使用 Fake Clock 或"演示触发"推进后，站内演示收件箱只出现一次通知。

**讲解要点**

- 模型只生成工具意图；服务端重新校验 user_id、参数、权限和时间。
- 写工具使用 idempotency key；Worker 采用 at-least-once 消费加幂等投递。
- 系统不声称 exactly-once；它保证用户可见副作用不重复。

### 3.5 演示四：搜索后总结

**用户输入**

> 搜索并总结 pgvector 适合个人助理记忆检索的三个原因，给出来源。

**预期可见行为**

- UI 显示工具开始、完成和摘要。
- 回复区分"来源事实"和"系统总结"，保留来源。
- Mock 模式下使用固定 fixture；不能称为实时搜索。

**讲解要点**

- 搜索 provider 是 adapter；P0 使用可控 Mock 确保离线可演示和可测试。
- 搜索正文属于不可信数据。即使网页包含"忽略之前指令"，也不能改变系统权限、调用高风险工具或泄露 Prompt。
- 空结果、部分结果、超时不会被模型补造成虚假来源。

### 3.6 演示五：外部依赖故障仍有可读回复

推荐只现场展示一种故障，其他故障使用预置截图或短录屏。

**操作**

- 在演示控制入口选择 `LLM timeout` 或 `Search timeout` fixture。
- 发送固定问题。

**预期可见行为**

- 页面在规定的总超时内结束加载。
- 返回"当前模型/搜索服务暂时不可用，可稍后重试"的可读回复，并带 request_id。
- 不出现无限 spinner、空白回复、原始栈或密钥。

**讲解要点**

- 429/暂时性 5xx 可有限重试；参数、权限、schema 错误不重试。
- Agent 有总 deadline、单工具 timeout、最大轮数和重复调用检测。
- 已产生的写副作用通过幂等键查询，不因用户重试而重复。

## 4. 可选加分演示

仅在主路径稳定且时间充足时选择一项：

- **SSE 断线恢复**：流式过程中刷新页面，最终消息恢复且用户消息不重复。
- **跨用户隔离**：使用用户 B 登录，直接访问用户 A 的 memory/todo URL，返回无权限/不存在语义。
- **上下文压缩**：加载预置长会话，展示 token 统计、摘要版本和保留的近期消息。
- **重复工具调用**：FakeLLM 连续返回相同调用，系统停止工具循环并进入 final round。
- **Trace 定位**：用 request_id 展示一次请求的 API、LLM、工具和 Worker 链路；确保字段已脱敏。

不要为了"加分"现场修改数据库、编辑代码或运行不熟悉的命令。

## 5. 演示数据与重置

### 5.1 演示账号

建议 seed 两个完全虚构的账号：

- `demo-a`：主演示用户，初始无咖啡偏好，包含一个可修改的普通待办。
- `demo-b`：隔离验证用户，包含文本相似但不同的偏好和提醒。

密码只存在本地演示说明或由 reset 命令输出临时值，不提交真实账号凭据。

### 5.2 固定数据

- 搜索 fixture：3～5 篇短文档，包含标题、来源 URL、摘要、发布时间。
- Prompt Injection fixture：正文中包含恶意指令，用于证明只把网页当数据。
- LLM fixture：正常对话、工具调用、畸形 JSON、429、5xx、超时、空答、重复调用。
- 提醒 fixture：固定 IANA 时区；Fake Clock 可推进到到期时刻。
- 长会话 fixture：恰好能触发一次 compaction，结果可重复。

### 5.3 重置方案

建议最终提供统一入口：

```bash
# 命令名称为目标模板，构建后以项目实际脚本为准
APP_ENV=demo make reset-demo
APP_ENV=demo make seed-demo
APP_ENV=demo make smoke
```

重置必须满足：

- 仅允许在数据库名、环境变量均明确为 demo/test 时运行。
- 幂等，失败时返回非零退出码，不打印"成功"。
- 清理旧会话、记忆、待办、提醒 job、演示收件箱和相关缓存。
- 重新生成固定账号、搜索数据和 Mock 场景。
- 输出当前版本、Mock/Live 模式、固定时区和基准时间。

不要在答辩现场手动执行 SQL 删除数据。

## 6. 主路径、故障路径与备选材料

### 6.1 主路径

1. 登录。
2. 告知并保存偏好。
3. 新会话主动使用偏好。
4. 明确遗忘并验证不再使用。
5. 创建、修改、触发提醒。
6. 搜索并总结来源。

### 6.2 故障路径

至少准备以下故障注入，但现场只选一个：

- LLM 429：有限重试后成功或降级。
- LLM 超时/5xx：总 deadline 内结束。
- 畸形工具 JSON：不执行工具。
- 搜索超时/空结果：不编造来源。
- Delivery 失败：提醒仍被记录，投递进入重试/失败状态。
- Redis 不可用：按设计区分可降级缓存与不可用调度能力。
- PostgreSQL 不可用：拒绝写入，不假装已保存。

### 6.3 断网或模型不可用备选

按优先级准备：

1. 本地 `FakeLLM + MockSearch + MockDelivery + FakeClock` 完整离线模式。
2. 已验证的备用模型 provider，仅在密钥和网络均可用时切换。
3. 主路径 2～3 分钟无剪辑录屏。
4. 故障演示短录屏和关键截图。
5. 静态架构图、SSE 事件样例和 trace 样例。

录屏要显示版本和 Mock/Live 标识；不要用录屏冒充当前现场实时结果。

## 7. 架构取舍与回答口径

### 7.1 为什么是 Next.js + FastAPI

- Next.js 负责交互、路由和流式 UI，React 生态适合聊天界面。
- FastAPI/Pydantic 适合明确工具 schema、接口契约和异步 I/O。
- Python 的 LLM、embedding 和数据处理生态更成熟。
- 代价是双语言工具链；通过 monorepo、OpenAPI 生成和统一命令降低契约漂移。

### 7.2 为什么 PostgreSQL + pgvector，而不是再引入独立向量库

- 用户、会话、消息、记忆、待办都需要事务和关系约束。
- 首版数据规模有限，pgvector 能在同一数据边界内完成语义检索，部署简单。
- 查询可以在同一 SQL 中先做 user_id/status/TTL 过滤，再做向量排序。
- 若未来检索规模或召回能力超出 PostgreSQL，再通过 repository/adapter 迁移，而不是首版提前复杂化。

### 7.3 为什么还需要 Redis

- Redis 用于短期状态、限流、SSE 事件缓冲、分布式锁/lease 和仅携 `job_id` 的任务通知队列。
- PostgreSQL 仍是业务真相来源；关键任务采用数据库 outbox，避免 Redis 数据丢失等于业务丢失。
- 首版不把长期记忆只放在 Redis。

### 7.4 为什么单 Agent，不做多 Agent

- 题目重点是记忆、上下文、工具稳定性和不确定性处理，不是角色数量。
- 单 Agent 的状态机、超时、成本和测试空间更可控。
- Tool Registry 已提供能力扩展边界；未来确有独立角色和收益证据时再增加多 Agent。

### 7.5 为什么不用企业 DSL 或直接复用企业内部仓库

- 企业 DSL 通常绑定内部鉴权、配置中心、模型网关、监控、发布平台和权限体系，脱离环境难以独立运行。
- 直接复用会带来授权、保密、依赖和可解释性风险，也不符合"从 0 到 1 完成可运行产品"的目标。
- 本项目复用的是成熟模式而不是代码：分层、注册表、幂等、重试预算、outbox、trace、脱敏和契约测试。
- 轻量实现更容易说明每一层为何存在，并对最终代码和质量负责。

### 7.6 为什么 P0 使用 Mock 搜索和提醒投递

- 答辩首先验证工具链的注册、校验、调用、结果处理和故障降级。
- 真实搜索/短信受网络、额度、审查和账号影响，会降低演示可重复性。
- Mock 与真实 adapter 使用同一接口和契约测试；它是可控依赖，不是假装真实联网。
- P1 可在不修改 Agent 核心的情况下接入真实 provider。

## 8. 常见评委问题与准确回答

### Q1：这和普通聊天机器人有什么区别？

普通聊天主要处理当前上下文；知伴增加了用户可控的长期记忆、跨会话检索、类型化工具、待办调度和异常降级。区别不在 UI，而在状态、权限和副作用的工程闭环。

### Q2：如何决定哪些内容应该记住？

明确"请记住"的内容优先；自动提取只允许白名单类型，并经过 schema、置信度、去重和冲突校验。寒暄和一次性事实默认不长期保存。用户可查看、更正和遗忘。

### Q3：模型说要记住，就一定写入数据库吗？

不是。模型只生成候选；服务端做确定性校验、用户归属、类型、长度、冲突和频率限制，符合策略后才写入。

### Q3.1：用户改变偏好（"不喜欢"变"喜欢"），记忆怎么处理？

不会记两条、也不会丢历史。主动记忆时走 `reconcile` 语义调和：模型判断新事实与现有记忆的关系（新增/更新/取代/重复），工程层校验 target 后执行。正反偏好（喜欢↔不喜欢）会 supersede 旧值，且通过 `superseded_by` 保留演化历史，能回答"你之前……现在……"。核心是"模型提议 + 工程裁决"，不让模型直接改库，杜绝幻觉误删。

### Q4：记忆检索如何排序？

先按 user_id、状态、类型和 TTL 做硬过滤，再组合语义相似度、置信度、时效等评分，使用稳定 tie-breaker。具体权重需要通过测试和使用反馈调整，不宣称它是唯一最优算法。

### Q5：如何避免不同用户的记忆串在一起？

user_id 来自认证上下文，不接受模型或前端传入的归属。repository、向量检索、缓存键、Worker payload 和工具执行都携带并校验 user_id；另有双用户相似数据的回归测试。

### Q6：用户要求"忘记"后，旧聊天里还有这句话怎么办？

活跃记忆会删除或失效，并创建 tombstone/版本记录；检索缓存和摘要引用同步失效。旧消息是否保留按会话数据策略处理，但后台不能从旧消息静默恢复已忘记事实。

### Q7：长对话会不会超 Token？

会，因此系统预先为 system、工具 schema、记忆、近期消息和输出分配预算；超过阈值时 flush 稳定历史并 compaction。单条输入超过预算则明确拒绝或要求缩短，不无限压缩。

### Q8：模型输出的工具 JSON 不合法怎么办？

在执行前用 JSON Schema/Pydantic 校验。可修复错误只进行有限修复/重试；仍不合法就不执行，并给用户可读说明。未知工具和额外字段不会被动态执行。

### Q9：为什么不能让模型直接访问数据库或网络？

模型输出是不可信的。所有能力必须通过注册工具，工具负责权限、参数、网络策略、超时、幂等和审计；否则 Prompt Injection 可能变成真实副作用。

### Q10：如何避免工具调用死循环？

限制最大工具轮数、总 deadline、单工具 timeout，并对规范化后的工具名与参数生成调用签名；重复达到阈值后停止，进入不再暴露工具的 final round。

### Q11：提醒怎么保证不重复？

不声称分布式系统 exactly-once。Worker 使用 at-least-once 消费，提醒版本与 idempotency key 约束数据库写入和投递，所以即使重试或崩溃恢复，用户只看到一次。

### Q12：时区怎么处理？

存储 UTC，同时保存用户 IANA 时区和输入原文；回复会回显绝对时间与时区。DST 缺失或重复时刻不能猜测，应请求确认或按明确文档规则处理。

### Q13：搜索网页包含恶意 Prompt 怎么办？

网页内容被标记为不可信数据，只能用于提取与总结，不能覆盖 system 指令、扩大工具权限或触发高风险副作用。URL 工具还需要 SSRF、重定向和响应大小防护。

### Q14：外部模型不可用，系统还有价值吗？

生成能力会受限，但系统应保持状态一致并给出可读回复，不假装已保存或已执行。离线 Mock 用于演示和测试；真实生产可以配置 provider 降级，但仍受总超时和成本限制。

### Q15：为什么不用 LangChain/LangGraph 等框架？

可按最终实现如实回答。若未使用：首版状态机规模较小，自有薄编排层更容易控制事件协议、重试、幂等和测试，不必引入额外抽象。若使用：只把框架当执行组件，权限、数据模型、幂等和观测仍由业务层控制。不要贬低框架，也不要声称自研普遍更好。

### Q16：你怎么证明系统稳定？

展示实际测试报告和故障注入结果，覆盖 LLM 畸形/429/5xx/超时、SSE 重连、工具幂等、Worker 重放、跨用户隔离、SSRF 和备份恢复。未实际执行的性能数字只称"验收目标"。

### Q17：项目中 AI 生成了多少代码？

按实际情况回答比例并不关键；重点是能解释核心状态机、数据边界、测试和取舍。提交代码需经过人工审阅、静态检查和测试，不能把"由 AI 生成"当作正确性证明。

### Q18：如果规模增长，哪里先成为瓶颈？

通常先观察 LLM 延迟/额度、SSE 连接数、向量检索和 Worker 积压。通过指标确认后，可拆分 Worker、增加连接/队列容量、调整索引或迁移独立检索服务；首版不预设微服务拆分。

## 10. 可量化验收目标

以下均为**验收目标，未实测前不得表述为实际结果**：

- MockLLM 条件下首个 SSE 事件 p95 小于 500 ms。
- 非模型 CRUD API 在 50 并发下 p95 小于 300 ms。
- 50 个并发 SSE 会话持续 2 分钟，错误率低于 1%。
- 10 万条记忆下 top-k 检索 p95 小于 300 ms。
- 1000 个到期提醒在 5 分钟内处理完成，重复可见投递为 0。
- 核心状态机分支覆盖率不低于 85%，全项目行覆盖率不低于 75%。
- 外部依赖失败后在配置的总超时内结束，无无限加载。
- 安全高危已知问题为 0。

答辩展示时应把目标与实测并列；若未达到，说明环境、差距、影响和改进计划，不选择性隐藏。
